# Abilities changelog

Abilities are this folder: `AbilityManager` and `AbilityBase`, the t0 abilities (Walk, Sprint, Jump, Dash, MeleeAttack, RangedAttack, Knockback, Death, Parry), `HitInfo`, ability steps (`steps/`), hit interceptors (`interceptors/`) and projectiles (`projectiles/`). What a hit or an ability does to a pawn is the effects system (`effects/`, its own changelog). Design: [docs/pawn/PAWN_SPEC.md](../../../docs/pawn/PAWN_SPEC.md), section 8 (8.3 to 8.6, 8.8 to 8.10, 8.15, 8.16, 8.20 to 8.24) and section 15. Overview: [README.md](README.md).

## Refactor candidates

## 2026-11-24

- **Generic settings** (the pawn redesign's build step 2, pawn spec 16.3; the owner's call): the 61 hand-written setting properties on `AbilityBase` and the kinds are gone. One `_get` and `_set` route any setting of the definition's class by name (`ability.cooldown_ticks`), for outside code, scenes and quick abilities (`self.duration_ticks = 30` in `_init()`; a bare name no longer compiles); writes still go to the node's own variant, with the error during play. Code inside abilities and the manager reads `settings.<name>` or the kind's typed reference (`_melee`, `_dash`), which is typed and faster than the old getters. A plain list written to a typed list setting takes the setting's array type (`set()` refuses it otherwise). Lost: compile-time checks and autocomplete on `ability.<setting>` from outside; a typo fails when the line runs. Not done: `_get_property_list` to show a node's settings as overrides in the inspector.
- **Steps run on the shared step core** (the pawn redesign's build step 2): `AbilityBase` owns a `StepTimeline` (`step_runner`) and forwards its step calls to it; `timeline` and `timeline_state` read through to it, and `started_at` keeps its start in step through delays and rollbacks. About 300 lines left `AbilityBase`. `AbilityStep` extends `Step`, keeping only its cancel window, ending on release and weapon point; `keeps_ability_running` is `keeps_owner_running`.
- **Ticks at 60 a second, and hits through the tick scheduler** (the pawn redesign's build step 1, foundations (pawn spec 16.10)):
  - Settings in seconds are now ticks at 60 a second: `duration` → `duration_ticks`, `cooldown` → `cooldown_ticks`, `buffer_window` → `buffer_window_ticks` (`AbilityDefinition`); `speed_up_seconds`/`slow_down_seconds` → `speed_up_ticks` (6)/`slow_down_ticks` (12) (Dash); `coyote_time` → `coyote_ticks` (6) (Jump); `max_charge`, `recharge_delay`, `min_start_charge` → `max_charge_ticks` (180), `recharge_delay_ticks` (60), `min_start_charge_ticks` (30) (Sprint); `max_lifetime` → `max_lifetime_ticks` (180) (projectiles). Saved definitions were converted (bolt, faction, finisher, heavy and second swings, heavy smash). `AbilityManager.ticks_for` is gone; `AbilityBase.duration_ticks()` is now `run_length_ticks()`, so the name is free for the setting. `HitInterceptor.active_seconds` stays in seconds until interceptors go (step 4).
  - Hits during simulate are booked with `TickDriver.scheduler` (after simulate, ordered by attacker's then target's entity number, then booking order); the static hit queue is gone. Hit lists and `HitInfo.attacker_id` use entity numbers (`HitInfo.key_of` is gone). Priority jitter rolls with `DeterministicRandom`.

New: `start_entry`, `stop_entry`, `running_entry_of`, `step_ticks_of`, `steps_after`, `step_before`, `timeline_loaded`. 300 pawns: unchanged (0.36 ms a frame).

## 2026-11-21

The node exports `kind` and `definition`; each setting stays readable on the node by its old name through a read-only property, so no reader changed. No definition: the kind's defaults, shared. One of another kind: the defaults, with a warning.

- The samples use definition files (`resources/abilities/`), the red hero's swings as variants of the faction's. Tests that changed a pawn's settings mid-test call `make_definition_unique()` first; new `ability_definition_selftest`.

- **Sprint runs on a charge** (the owner's call), replacing its 3-second duration and 4-second cooldown: `max_charge` 3 s, `recharge_rate` 0.5, `recharge_delay` 1 s, `min_start_charge` 0.5 s (so a held key on an empty charge doesn't flicker it on). Two pushed values set only when it starts or stops; `ready_at` is when it can start again.
- **A timed locomotion's time waits again while an action pauses locomotion** (`delay_run()`, new), as before deadlines; part 1 had lost it. The built-in Dash locks Sprint out, so this is for one that doesn't.

- **Ability state is pushed to the state store** (abilities step, part 1; state store spec 13.10): every built-in ability's rolled-back properties have setters that call the new `AbilityBase.push_state`, and the manager registers them as pushed entries, so the commit reads no ability node. `get_pushed_properties()` (new) lists them; `get_rollback_properties()` stays for properties read at every commit and is empty in the base; `keeps_state()` (new) asks either. Steps write their numbers through `set_step_value()` (new): GDScript doesn't call a setter for one element of a packed array, which the rollback test caught. At 300 pawns the commit went from about 1.5 to 0.7 ms a tick.
- **Timers are tick deadlines** (ability spec 4): `ticks_left`, `cooldown_ticks_left` and `buffer_ticks_left` are replaced by `started_at`, `ends_at`, `ready_at` and `buffer_until`; the manager's `combo_window_ticks_left` by `combo_open_until`; Jump's `ticks_off_ground` by `left_ground_at`. Knockback's fade and Dash's phase read `ticks_before_this_run()` (new); Death runs with `ends_at = NEVER` while Health is 0. The manager no longer counts anything down: it keeps the soonest deadline ahead (`_next_deadline`) and moves `readiness_version` on when it passes, and works it out again after a rollback load (`state_loaded()`, new). New: `is_timed()`, `is_run_over()`, `end_run()`, `is_buffered()`, `is_combo_window_open()`, and read-only `ticks_left()`, `cooldown_ticks_left()`, `buffer_ticks_left()`, `combo_window_ticks_left()`, `ticks_off_ground()` for readouts. A run started between a load-step pawn's runs now counts from its own start tick. A cooldown now counts as over from the start of its last tick, so `readiness_version` notices a passed deadline when it's read (the AI asks in the input step, before the abilities run); `ai_batch_decider_selftest` caught the AI's kept answer being one step late.

## 2026-11-17

- **One override check:** the AbilityManager asks `ScriptOverrides.overrides()` (`platform/`) whether an ability's script has its own `every_tick()` or `can_start()`, instead of two copies of the check of its own.
- **What can start, kept for the AI** (scaling spec 6.2, step 5b; the owner: "event based seems to be better overall"). `AbilityManager.readiness_version` goes up by one whenever something changes that can change what `can_start` answers: an ability starting, finishing or being cancelled, a step starting or ending (`AbilityBase.start_step`, `stop_step`, for its cancel window), a cooldown or the combo window running out, the combo window opening, timers changing, the abilities being collected again, and the pawn's effects changing (`readiness_changed()`, which `EffectManager` calls, for priority boosts). The AI asks `can_start` again only after it moves on (`AIInputs.action_ready`), instead of at every decision. An action with an ability whose script has its own `can_start()` (Jump needs the ground, Dash may) is asked every time: `ready_follows_body(action)`, worked out when the abilities are collected. `ai_batch_decider_selftest` checks the kept answer against `can_start` at every decision of a real fight.
- **`can_start(action)` looks only at the abilities on that action** (an index, `_by_action`, built with the abilities), and the conflict check looks only at abilities with a timer while that list is up to date (`_timed`; never rebuilt there, since `_run_actions` loops over it while it asks, and out of date it falls back to every ability). The same answers; the AI asks `can_start` at every decision for each behaviour that presses an action. The saving measured small at 600 pawns: the cost is mostly GDScript's per-call overhead, not the loops.
- **Hit interceptors** (pawn spec 8.23, the owner's call: "leave space for stats and proceed as proposed"). `HitInterceptor`, a node under an ability or one of its steps, can stop a hit while its parent runs: MISS (`InvulnerabilityInterceptor`, the hit never arrives) or TURN_AWAY (`ParryInterceptor`, hits from the front; the hit arrives, then `intercept()` decides). The first active one that stops a hit ends it, `AbilityManager.hit_intercepted` goes out, and its `ON_INTERCEPT` effects go back to the attacker in a hit marked `HitInfo.from_interception`, which can't be turned away. Dash and Parry make a default interceptor when they have none (`make_default_interceptors`). This replaced the special cases: `AbilityBase.invulnerable_while_running`, `invulnerable_seconds`, `on_parry_effects`, `on_parry_self_effects`, `has_invulnerable_step()`; `AbilityStep.invulnerable`; `AbilityManager.parry_hit()` and its parry and invulnerable lists; `ParryAbility.try_parry()`, `faces()`, `front_degrees` and the `parried` signal. `EffectApplier.ON_PARRY` became `ON_INTERCEPT` with the same saved number.
- **Swing hits in C++.** When nothing would be rewound (AI swings, offline play), `MeleeSweepStep` asks the pawn grid (`AIPawnGrid.find_touching`) who its spheres touch, instead of a physics query per spot. Same answer; physics without the C++ library, lag compensation when it rewinds.
- **One Health stat** (the owner's call). `DeathAbility.health_stat` went: Death watches `StatManager.HEALTH`, as hits and the EffectManager's death check do, so the two can't disagree.
- **The AI through its core.** A swing's warning goes to the target's `ai_context.note_incoming_attack`.
- **Comments cleaned up** for the documentation pass: dated notes moved here, doc comments in Godot's markup. Stale comments fixed: MeleeAttack's header (hits are its sweep step's, Dash's priority is 40, its turning is the TurnToFace step's), Knockback's and Parry's interrupt numbers against Dash (its threshold is 25, its priority 40), what starts Knockback (a KnockbackPart's `push`) and Death (`AbilityManager.health_ran_out`), which abilities override `duration_ticks` (Dash, Knockback, Death; not MeleeAttack), the interrupt numbers' list, `hit_arrived` (before an interceptor, not "a parry"), `step_finished`'s reasons ("released" too) and the hit order in `receive_hit`.

## 2026-11-16

- **Ability steps** (pawn spec 8.20, agreed with the owner over several rounds). An ability can be built from `AbilityStep` children that start each other (`starts_first`, `starts_when_finished`, `start_step()`), run side by side, give cancel windows (a step's `interrupt_threshold`) and end the ability when none that keeps it running is left (`keeps_ability_running`, `max_steps_ticks` as a safety). A step started during a tick gets its first tick on the next. Steps: `WindupStep`, `TurnToFaceStep`, `MeleeSweepStep`, `WaitStep`, `OpenComboStep`, `ApplyEffectStep`. `step_started` and `step_finished` signals; the replay records each step.
- **MeleeAttack built from steps.** Its hit checks moved into `MeleeSweepStep`; with no steps of its own it makes Windup, TurnToFace, Sweep, OpenCombo and Recovery from its settings, so every swing in every scene became a stepped one with the same numbers. Its `duration_ticks`, `tick` and rollback list went; `_hit_this_swing` became `AbilityBase.pawns_hit_this_run`.
- **Holding** (the owner's call: the base's, not one step's). A step with `ends_when_released` ends with "released" on the first tick its action isn't held (`while_held`, or the ability's trigger action), from rolled-back input. The turn follows the look only while the attack is held, and turns at least `min_turn_degrees` first however short the press. The windup's timer waits until the pawn is within 90 degrees of the look. `windup_turn_degrees_per_second` defaults to -1: the pawn's TurnRate stat.
- **Combos by position.** `combo_positions` on each ability and one counter on the manager (`combo_position`, `combo_window_ticks_left`, both rolled back); `OpenComboStep` opens the window after a hit.
- **Step state as one value.** Every step's `running` and `step_ticks` live in its ability's `step_state`, recorded as one value: two values per step cost 2.4 ms a tick at 150 pawns. A safeguard stops steps that start each other in a loop (`MAX_STEP_STARTS_PER_TICK`, 32).
- **Pawns that run every 2nd or 4th tick** (pawn spec 8.21): timers, step counts, Jump's time off the ground and Death's hold advance by `ticks_elapsed`; a sweep covers every tick its run covers (`centres_for_ticks`).
- **`needs_full_movement`** (pawn spec 8.22): Dash and Knockback move by physics, not the crowd mover.
- **Hits and death on the AbilityManager** (pawn M3, pawn spec 8.16). `receive_hit`, the hit queue, `is_invulnerable`, `health_ran_out`, `revive` and the `hit_arrived`, `hit_received` and `died` signals moved here from `Pawn`. Each part cleans up after a death by listening to `died`.
- **Input on the ControllerManager** (pawn M4): abilities read it through `move_input()`, `look_yaw()`, `held_actions()` and the rest, which answer "nothing pressed" without one.
- **From the wider code audit.** `start_ability` on a running ability ends its run properly first (it sent `ability_started` twice with no finish between, and never restarted its steps), and if it may not restart the run carries on. An ability started by an earlier ability's press in the same pass no longer gets an extra tick (`_started_later`). A running ability keeps the pawn awake unless it says it can wait (`can_sleep_while_running`), so a corpse sleeps. `get_knockback()` is found once; `is_action_running()` asks only running timers. `run_steps` and the sweep's physics query reuse their objects, and the sweep leaves at once in a replay.

- **Effects replace numbers** (pawn spec 8.11, the owner's design). `HitInfo` carries `effects` and `attacker_effects` instead of `damage`, `knockback_speed`, `knockback_ticks` and `knockback_hop`, and gained `damage_dealt` and `planned_damage()`. An ability's `EffectApplier` children are collected once (`on_start_effects`, `on_hit_effects`, `on_hit_self_effects`); on-start effects apply on every machine. Effects can add to priority and interrupt numbers while they last (`press_priority_now`, `interrupt_priority_now`, `interrupt_threshold_now`), which is how combos worked: `FollowUpAttackAbility` went, replaced by boosts, and a buffered press lets every ready ability on its action compete.
- **Tags** (pawn spec 8.10): abilities set their categories from `Tags` constants; `extra_categories` (groups such as `movement.basic`, `movement.advanced`); `action_for_tag` for the AI; `cancelled_by` for exceptions to the numbers; `get_interrupt_table()` and `interrupt_rule()` share one rule with starting.
- **Dash reworked** (the owner's design, pawn spec 8.9): two phases by acceleration (100 m/s² for 0.1 s, then 50 for 0.2 s, never backwards) instead of a flat 18 m/s for 0.15 s with the speed cut after; cooldown 2 s (was 1); interrupt priority 40 (was 20), the one thing that cancels a knockback; threshold 25 (40 for a few hours) so a knockback cancels it once its invulnerability is over; invulnerable while it ran; usable in the air; `pauses_locomotion` so Walk doesn't fight it.
- **Knockback:** a small hop back (the owner's request), and threshold 35, so only Dash cancels it.
- **Game feel for swings:** the hit sphere sweeps across an arc (`sweep_degrees`, `sweep_from_left`), checking every spot it passes through in one lag compensation rewind; it turns during the windup; `hit_area_moved` for debug drawing.
