# AI changelog

The AI is this folder (the context, sensing, memory, target selection, states and behaviours), the AI controller that acts for it (`controllers/AIController`), and its C++ side in `native/src/` (`AIMemoryStore`, `AIPawnGrid`, `AISensingJob`, `SightGeometry`, `ai_sight_rules.h`). Design: [docs/pawn/PAWN_SPEC.md](../../../docs/pawn/PAWN_SPEC.md) section 10, and [docs/scaling/SCALING_SPEC.md](../../../docs/scaling/SCALING_SPEC.md) sections 3 to 7 for the C++ and worker-thread parts. Overview: [README.md](README.md).

## Refactor candidates

Code that works but doesn't yet fit the project's goals (reusable, extensible, efficient, designer friendly). Each is marked `REFACTOR:` in the code. Sizes are rough: S an hour or two, M a day, L more.

One shared helper (on Pawn, say) is one place to change | S |

## 2026-11-17

- **Streamlining from the duplication audit** (the owner's go-ahead). One point of interest: `AIContextComponent.point_of_interest(within_ticks)` replaces the copy of `_point_of_interest()` in Look Toward and Investigate, and `AIInputs.half_noticed_conditions()` their two identical condition lists, so the two react to the same things. One group lookup a tick: `AIInputs` asks the tree for a group's nodes at most once a tick and shares the list between pawns (each still looks for its nearest every 2 s), instead of every pawn asking for it. One override check: `ScriptOverrides.overrides(script, function)` (new, `platform/`) replaces four copies of "does this script override that function" (two in the AbilityManager, `AIBehaviourBase.has_own_code`, `AITargetSelector`'s `target_priority` check). Both refactor rows for the first two are gone.
- **C++ is the main path** (the owner's call, correcting how the plan read): GDScript's decider is a dormant backup that runs only without the C++ library or when switched to by hand to find a fault, and the reference the tests compare with. The earlier "each pawn deciding on its own is the default" meant each pawn deciding for itself rather than in groups, in whichever language. Scaling spec 6.2, the roadmap and the batcher's description say so now.
- **Look first, then go and see** (the owner's call: Look Toward can make the AI certain more cheaply, so it goes first, and once Investigate starts, Look Toward shouldn't catch until Investigate cools off). Look Toward already scored above Investigate (0.6 against 0.5), but stepped aside only through a 3 s cooldown, after which it could cut into a running Investigate. Now it has no cooldown and a negative persistence instead (-0.3, held 600 ticks, fading over 300): once it has looked, it scores 0.3, below Investigate, so Investigate runs and Look Toward stays out of its way; it gets a turn again only when Investigate can't run (its 120-tick cooldown after finishing). `min_run_ticks` is its look (60), so the penalty that starts with it doesn't cut the look short. `ai_stealth_selftest` checks the order and that Look Toward never replaces a running Investigate.
- **Conditions as data, and behaviours that sleep until woken** (scaling spec 6.2, step 5b; the owner's calls: "data as IO for C++ looks like the winning move", no behaviour written in C++ because hardcoding the move set "feels anti-designer", and events where they apply). The spec's 6.2 is rewritten as agreed, with steps 5a to 5f and 6.3 (a significance manager, later).
  - **Inputs:** `AIInputs` (new, `context.inputs`), one per pawn: named numbers with a slot each, the same slots for every pawn. Built-in ones are worked out once per decision, only those the brain's conditions read (`target_distance`, `most_aware_certain`, `most_aware_uncertain`, `ticks_since_unknown_hit`, `incoming_attack`, `incoming_attack_tick`, `incoming_attacker`, `group_distance/<group>`, `group_found/<group>`, `action_ready/<action>`); any other name is a game's own, written when it changes (`set_input`). Names starting `ticks_` are times, converted to the match's rate. Go To Point's nearest-node search (every 2 s) moved into it (`nearest_in_group`).
  - **Conditions** (new, `ai/conditions/`): `AICompareCondition`, `AIChanceCondition` (replayable, optionally once per input value), `AIAnyCondition`, and `AIScoreCurve`, which scales a behaviour's score between `min_score` (or 0) and `max_score`. Behaviours have `conditions` and `score_curves` settings for designers, and build their own from their settings (`own_conditions()`): Attack (target within the swing's reach minus `approach_margin`), Go To Point (a node in the group, further than `arrive_radius`), Look Toward and Investigate (something half-noticed, or an unknown attacker's recent hit), Search (the most aware entry certain), Parry (a swing coming, and its roll). `is_available()` and `score()` now check them by default; none of the built-ins overrides either any more. A behaviour that does (`has_own_code()`) still works; the C++ decider asks GDScript for it.
  - **Parry's roll** is keyed by the attacker's pawn number (`AIContextComponent.number_of`, new) instead of its instance id, which differed between runs, and mixes in the behaviour's name hash, as every chance condition does. Which swings get parried changes once; it's still about 30%, once per swing, and replays the same.
  - **"Could this action start?"** is the input `action_ready/<action>`, asked of the AbilityManager again only after its `readiness_version` moves on, or every time for an action whose ability has its own `can_start()` (the abilities changelog). The behaviour manager's hard rule and the batcher read it.
  - **The behaviour manager** starts each decision's inputs afresh (`AIInputs.begin_decision`): each is worked out the first time a condition reads it, so a decision pays only for what the behaviours its early stop reaches read. A decision record or the batcher's row needs them all (`fill`, with the slots from `_worked_out_inputs()`, listed once; `inputs_changed()` lists them again after `AIBehaviourBase.rebuild_conditions()`). The first version worked out every input at every decision, and deciding cost 64 µs instead of 46. `describe()` gives each behaviour's scorer ("conditions", or "given" for own code), conditions and curves. Decision records hold the inputs (`AIDecisionRecord.inputs`), and `decision_replay.gd` passes them to C++.
  - **The batcher** no longer calls `is_available()` and `score()` for behaviours judged by conditions; it copies the pawn's inputs into the row. A bug found on the way: the row kept the pawn's own inputs array rather than a copy, so a later decision overwrote it and C++ judged Parry against later inputs (3 disagreements in 1 484); fixed with `duplicate()`.
  - **Wake-ups:** a running behaviour's `tick()` runs when something it waits for happens, `wake_on_path_end()` (`NavigationManager.path_ended`, new), `wake_on_action_end(action)` (`AbilityManager.ability_finished`, `ability_cancelled`) and `wake_at(tick)`, with `tick_interval_ticks` the longest it sleeps. Go To Point, Wander and Search sleep up to 60 ticks (were 5) and wake when a walk or pause ends; Attack and Parry (were every tick) wake for the press, two ticks later, and when the swing ends. Attack's aim follows its target every tick through the AI controller (`look_at_node`, new) while it sleeps; it re-aimed at the target's last known position every tick before, which sensing keeps close to the target while it's in view. Chase, Look Toward and Investigate keep their 5-tick interval: following something that moves is regular work.
  - **Measured** (the mass battle, 600 pawns, spawns 40 m out, 90 s, `--scopes`, against the same run this morning): GDScript's deciding about 50 µs a decision against 46 (2.74 ms a tick against 2.45; parts this didn't touch read 3 to 8% higher too, so some of it is the machine); behaviours' ticks 1.25 ms a tick against 1.30, Go To Point's 4 ticks a tick against 34, Heavy Attack's 2.6 against 9.9. Shadow mode agreed on every decision, 290 989 at 600 pawns and 72 461 at 150, and gathering a row costs 33 µs (was 45), now mostly the per-behaviour state (cooldowns, persistence), which step 5c moves into C++. The gain on the main thread comes when the batch's answers are used (5e); until then the default GDScript path costs about what it did.
  - Tests: `ai_conditions_selftest` (new: inputs, every condition kind, curves, `has_own_code`, and C++ judging made-up brains with random inputs the same way, 1 500 of 1 500); `ai_batch_decider_selftest` also checks the kept `action_ready` against `can_start` at every decision of a real fight (3 525 checks); `ai_behaviour_manager_selftest` checks the wake-ups; `ai_go_to_point_selftest` found Go To Point running with no rally point (an absent group reads as far away), fixed with `group_found`.
- **Deciding twice a second instead of four times** (`mass_battle_measure -- --decision-interval=N`, new): at 600 pawns it saved only about 20% of deciding (3.3 to 2.6 ms a tick, about 54 decisions a tick down to 40), because events (hits, swings coming, state changes, behaviours ending) drive about 40% of decisions in a fight, and the fight went about the same. The interval stays 15; making it change with load belongs to a significance manager (scaling spec 6.3).
- **Decision records and finer timings** (scaling spec 6.2, the first piece of the "shadow" C++ decider, which decides beside this one without being used until it agrees). Each decision can now be recorded: `AIDecisionRecord` (new) holds what it was made from (its cause, reason and state, the running behaviour, and each behaviour's hard rule, persistence, jitter, ceiling, floor, availability and score) and what it chose. The behaviour manager fills one in only while `AIBehaviourManager.decision_listener` is set (static, one for every manager), and `decide()` takes the record to fill (`run_ai` passes one holding the target and state before and after their updates). `ai/debug/AIDecisionRecorder.gd` (new) keeps them, describes each pawn's brain once, and saves JSON lines; `mass_battle_measure -- --record-decisions=<file>` records a fight. New scratch values on behaviours (`decision_score`, `decision_scored`). New timing scopes: `ai.decide.target`, `.state`, `.behaviour`, `.switch`, and one per state (`ai.state.<name>`), behaviour check (`ai.available.<name>`), behaviour tick (`ai.behaviour.<name>`) and sense (`ai.sense.<name>.full` and `.refresh`), plus `ai.sense.search` and `ai.memory.forget`; the names are made once (`perf_*_name` on behaviours, states and senses). Test: `ai_decision_recorder_selftest`.
  - **The C++ decider, `AIBatchDecider`** (native; shadow decider step 5b's first slice): makes the same decision from plain data. `ai/tests/decision_replay.gd` replays recorded decisions through it, `ai_batch_decider_selftest` checks every rule with made-up brains and a real faction arena fight, and `ai_batch_decider_compare -- --file=<recording>` checks a saved fight. Every decision agreed: 32 794 at 150 pawns and 194 622 at 600, at 0.2 to 0.4 µs a decision. Behaviours' own checks are still GDScript's answers (the "given" scorer); `decide()`'s doc now says a change to it goes in both. The recorder saves numbers at full precision and describes `min_run_ticks_at_rate`.
  - **Live shadow mode: `AIDecisionBatcher`** (new GameMode module, off by default; not in the project's module list, so a game or a tool adds it: `GameMode.add_module`, `mode = SHADOW`). As each decision starts, it gathers the pawn's inputs from the live pawn into a row (the manager calls `decision_batcher.gather()` and `note_answer()`, a new static hook like `decision_listener`); at the end of the tick one C++ call decides every row, and the answers are compared and counted (`get_counts()`, the first disagreements as warnings). It asks `is_available()` and `score()` of every behaviour that passes the hard rules, before GDScript does, at the same tick, so batched deciding needs both to be safe to call twice (every t0 behaviour's are). The brain description moved from the recorder onto the manager (`AIBehaviourManager.describe()`). `mass_battle_measure -- --ai-shadow` runs it. Measured: every decision agreed, 48 519 at 150 pawns and 190 828 at 600 (up to 77 a batch); at 600 pawns gathering the rows in GDScript costs 2.7 ms a frame (about what GDScript's judging costs), the C++ call 0.02 ms, building and comparing 0.08 ms. So the inputs are the next cost: the "can this action start" bits (a mask the AbilityManager keeps), cooldowns and persistence as per-pawn state in C++, and native scorers for availability.
  - **The fine scopes are detailed ones** (`PerfScopes.begin_detailed`): per state, behaviour check, behaviour tick, sense, the sensing search and memory's forgetting time only while F4 is open or with `--scopes`; they cost about 0.2 ms a frame at 600 pawns. Timing scopes also inflate what they sit inside: `can_start`, measured as 1.0 ms below, was nearer half that. Gathering a row in shadow mode costs about 45 µs, spread over GDScript's calls for each of about nine behaviours, so faster loops won't remove it; keeping the inputs in C++ will.
  - What they showed, the mass battle at 600 pawns (spawns 40 m out): the behaviour manager's judging costs 2.8 ms a frame, but the behaviours' own `is_available` checks only about 0.3 ms of it. Temporary scopes inside it (removed again): the hard rules and ranges 1.8 ms, of which `AbilityManager.can_start` alone was 1.0 ms; sorting for the highest floor 0.5 ms; scoring 0.2 ms. At 150 pawns over 40 s, 32 794 decisions: 88% kept the same behaviour, 11% were held by the interrupt rule, 2.3 availability checks per decision, and every pawn had the same brain.
